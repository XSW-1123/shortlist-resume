# Phase 1 JD 拆解与考点清单

目标：把「面试官会在意什么」从经验判断变成有出处的清单，作为 R7 双闸门的第一道门。

## 1. JD 四桶

把 JD 原文逐条拆进四桶，保留条目编号（后续台账要引用条目号）：

| 桶 | 内容 | 对简历的动作 |
|---|---|---|
| 硬门槛 | 学历、专业、届别、城市、实习时长 | 只在页眉 / 教育背景如实呈现，改不了也不粉饰 |
| 核心技术词 | 语言、框架、数据库、中间件、工具链 | 技术名词与 JD 写法**逐字一致**（搜索是字面匹配） |
| 能力要求 | 原理、并发、一致性、排查、设计取舍 | 转成项目 bullet 的可追问考点，不写形容词 |
| 加分项 | 业务领域、开源、竞赛、云、AI | 有证据才写；无证据进「主动放弃的 JD 关键词」清单 |

## 2. Top 12 关键词

用 `scripts/ats_match.py` 的口径抽取：英文技术词出现 1 次即计入，中文 2–4 字 gram 需出现 ≥ 2 次；去掉「熟悉 / 熟练 / 者优先」等招聘话术停用词；同义子串去重后取前 12。

```
python scripts/ats_match.py jd.md draft.txt
```

注意：匹配分只用于同版回归（R15）。删内容会让「前 1/3」权重区前移、分数虚高；把技能栏移到文末会让分数回落但全文命中数不变。两种情况都不回调顺序、不加词刷分。

## 3. P0 / P1 权重分层（岗位无关的做法）

按「被问到的概率 × 答不上来的代价」给 JD 技术词分层，并把依据写清：

- **P0**：地基类，几乎必问且能连问三层。写进技能栏和项目 bullet，逐字命中。
- **P1**：项目深挖类，用来出追问链。主要落在 bullet 的「为什么 / 边界 / 代价」。
- **P2**：趋势类加分项，没有真实证据一律不写，转成面试口述的选型对比。

没有联网或没有岗位专项资料时，不要凭空造「2026 权重表」：直接用 JD 条目编号 + 用户提供的面经 / 岗位资料作为权重来源，并在 `report.md` 说明来源。内置 `references/java-backend-profile.md` 只是 Java 后端的参考档，其他岗位用 `assets/role-profile.template.yaml` 现场生成。

## 4. 难度闸门（三层追问自测）

对每个准备写进简历的重要技术词，写出三层问题并确认用户能答到第三层：

```
第一层：它怎么用 / 参数是什么
第二层：失败场景、边界、并发与一致性问题
第三层：为什么不用替代方案、线上故障怎么排查、代价是什么
```

扛不住第三层的词：降级为「了解」或删除，不要靠「精通」「熟练掌握」掩饰。例：分布式锁 → 误删 / 可重入 / 续期 → 主从切换失效；缓存 → 一致性 → 旧值回填窗口 → 降级策略。

## 5. 无证据词黑名单

按岗位列出「常见但用户项目里没有」的词，例如投 Java 后端时常见的 MQ、SpringCloud、Docker、虚拟线程、JVM 调优、压测 QPS、上线部署、AI 大模型。名单由用户项目实际情况生成，不是固定表：凡用户无法指出源码 / 证据出处的词，一律进黑名单。

项目里确实没用某组件时，把「为什么用现有方案、它的兜底是什么」写清楚，让面试官自然问出「为什么不用 X」，并提前准备选型对比。这比硬塞一个没用过的词更安全。

## 6. 输出物

Phase 1 结束必须在 `report.md` 里留下：

1. JD 四桶表（带条目编号）
2. Top 12 关键词及其 JD 频次
3. P0 / P1 清单与权重来源（JD 条目号或可核验资料 URL）
4. 每个 P0 词的三层追问链
5. 「主动放弃的 JD 关键词」及放弃原因
6. 无证据词黑名单
7. 技能栏排序依据（对齐哪几条 JD 任职要求；若沿用旧顺序，写明「为什么不改」）
