# 现行有效规则总表 R1–R18（唯一执行入口）

本文件是全部现行规则的唯一权威来源。与 `SKILL.md`、README 或任何历史版本说明冲突时，以本文件为准。规则只放「现行有效」；论证、实证与演进记录不属于执行依据。

新增规则前先问：它兜住的是 0.2 里哪一类已发生过的失败模式？没有对应失败模式的规则不要加。

## 0.1 R1–R19

| ID | 规则（一句话） | 验收口径 |
|---|---|---|
| R1 | `项目经历` 板块 100% 与目标岗位同技术栈；无关项目处置优先级：整块删除 > 压进 `education.highlights` 1–2 行略写 > 只进面试口述 | 项目板块非岗位技术词 0；岗位相关字符 100% |
| R2 | 只用标准板块名 `教育背景` / `项目经历` / `专业技能`（有实习加 `实习经历`）；禁止 `补充信息` / `其他信息` / `荣誉奖项` / `科研与荣誉` | 自造板块名命中 0 |
| R3 | 顺序 `教育背景 → 项目经历 → 专业技能`；项目在技能之前、占全文 ≥ 60% 字符；用 `section_order` 显式声明 | PDF 与 DOCX 顺序一致，项目板块 ≥ 60% |
| R4 | 证书 / 奖项 / 科研成果 / 横向课题压在 `education.highlights`，最多 2 行、行内标签、不展开、不带争议数字 | 略写行 ≤ 10% 全文字符 |
| R5 | 逐行审计：按行导出 PDF 文本层，逐行问「这一行能被追问出哪个目标岗位技术细节」，答不上来就删；主修课程、业务流程叙述、工作总结式 bullet、置顶自我评价一律删 | 项目板块弱相关行 0 |
| R6 | 技能栏只负责关键词命中；实现级细节（某个 SQL 子句、某个 Lua 脚本、某个注解名、某个回调钩子）由项目 bullet 独占 | 技能栏实现级细节词 0 |
| R7 | 技术词双闸门：① 在面试官 P0/P1 考点清单或目标 JD 里（权重）**且** ② 在项目源码 / `evidence/` / 采集表能指出处（可核验）；缺一不写 | 逐行证据台账齐全，`report.md` 必交 |
| R8 | 技能排序按岗位匹配度不按学习顺序；第一位必须是该岗位最核心的语言与框架；顺序对齐 JD 任职要求条目，经复核一致的顺序不得为显示改动而调整，但要写明「为什么不改」 | 报告给出排序依据与 JD 条目号 |
| R9 | 程度词三级：`熟悉`=有源码落点 / `理解`=知识层必考但项目无实现 / `了解`=只划认知边界；全篇 0 个「精通」 | 精通命中 0，同条内程度词不自相矛盾 |
| R10 | 难度闸门：写下的词要能扛三层追问；无真实证据的词一律不写，缺口转为面试口述的选型对比 | 无证据词命中 0；缺口清单在报告 |
| R11 | 项目 bullet 走 PQR（问题 → 方案 + 技术 + 参数 → 可核验结果或明确边界），且至少一处「为什么 / 边界 / 代价」；渲染 ≤ 2 行；一条 bullet 一个可追问考点 | 全部 ≤ 2 行；无「显著提升」「参与 / 协助 / 负责」 |
| R12 | 同一事实全文只有一套数字，每个数字在 `evidence/numbers.md` 有测量方式；两套口径冲突时整组弃用 | 争议数字 0 |
| R13 | 交付链路一致性：新版成为推荐版后，同步 `deliver/` 的 4 件产物与 `source.yaml`；旧版留在 `apps/`，做字节级 + PDF 文本层逐字校验 | `validate.py` 全绿 |
| R14 | 版式：1 页 A4、单栏、文本型 PDF、无表格 DOCX、页边距 1.2 / 1.2 / 1.8cm、正文 ≥ 10pt、注释 ≥ 9pt、行距 1.15–1.3、单一主色、底部留白 5–15%、无孤字 / 重叠 / 截断 | 脚本实测 + 放大目检 |
| R15 | 匹配分不作优化目标，只用于同版回归；掉分须逐词 diff 归因，若为脚本 2-gram 或「前 1/3」口径效应，不回调顺序、不加词刷分 | 报告写出归因 |
| R16 | 每次升版必交 `report.md`（含逐行证据台账 + 实测表），并运行 `scripts/validate.py` 全绿后才算交付 | 校验退出码 0 |
| R17 | 证据必须落到 URL / 文件行号 / 命令输出，禁止「我查过了」这类不可核验结论；报告按「内容 → 来源 → 面试官权重 → 项目证据 → 三层追问链」逐行给出 | 台账无空来源行 |
| R18 | 展示给用户前，检查用户实际会打开的文件（`deliver/`），不是只看刚生成的 `apps/` 深层产物；所有结论以该文件的文本层为准 | `validate.py` 比对 `deliver/` PDF |
| R19 | **项目块三层标签 + 条内局部加粗**：条目自上而下必须是 `名称 → 技术栈 → 项目简介 → 技术亮点`，标签加粗、内容常规；bullet 加粗只落在「机制名 / 方案名 / 关键参数 / 关键数字」，整条加粗＝没有重点；每条 1–3 处，粗体**视觉宽度**（汉字 1.0 / 西文 0.55 加权）≤ 该条 45%；技能栏只加粗分类名，行内不加粗（会加宽字面把满宽行挤折） | 每条 ≥ 2 处粗体且视觉宽度 ≤ 45%（`validate.py` 按 span bold flag 机检）；技能行不折行 |

## 0.2 六轮失败模式登记册

| 轮次 | 用户反馈（原话摘要） | 真实根因 | 现在由谁兜住 |
|---|---|---|---|
| 1 | 「和之前没啥变化」「内容这么杂」 | 只改措辞不改结构，把压缩弱相关项目当成解决 | R1 + 按板块扫描 |
| 2 | 「还是有不相关的内容」 | 根目录同名成品自始至终是旧版，用户打开的不是新稿 | R5 + R13 + 交付链路校验 |
| 3 | 「其他能增加经历厚度的东西也可以加，但要略写」 | 为纯净把真实经历全删了，矫枉过正 | R4 |
| 4 | 「别人优秀的简历哪里有补充信息」 | 为略写自造板块名，载体错了 | R2 + R3 |
| 5 | 「面试官在意什么，选词和排序都要有迹可循，还要考虑难度」 | 技术词靠经验选，无权重来源、无源码核验、没考虑三层追问 | R7–R10 + R17 |
| 6 | 「总结完善优化这个工作流」 | 规则层层打补丁散落十余处，摘要与正文失同步 | 本文件单一入口 + R16 + `validate.py` |

## 0.3 升版 SOP

**动手前**：读 R1–R18 → 确认本轮要兜住的失败模式 → 若是新失败模式，先补检索与实证，再补规则编号 → 不为「有改动」而调整已与 JD / 实证一致的结构。

**动手后（缺一不算交付）**：
1. 渲染新版到 `apps/日期-版本/`，含 PDF / DOCX / preview / `resume.typ` / 内容源副本 / `report.md`；
2. 按 R5 逐行审计、按 R7/R17 写逐行证据台账、按 R14 放大目检；
3. 旧版保留在 `apps/` 不删 → 同步 `deliver/` 四件产物 + `source.yaml`（R13）；
4. 更新 `report.md` 实测表与归因说明、投递台账追加一行；
5. 运行 `scripts/validate.py`，全绿且退出码 0；
6. 把 `deliver/` 里的文件呈现给用户，并说明本版相对上一版改了什么、为什么改、哪些内容经复核后没改。

## 0.4 已作废、不得复活的旧规则

- 「弱相关项目压缩到 1–2 条、占版面 ≤ 30%」以及任何 ≥ 70% 相关性阈值 → 已被 R1 一票否决取代
- `补充信息` / `其他信息` / `荣誉奖项` / `科研与荣誉` 等自造板块名 → R2 禁止
- 技能栏排在第二个板块、`awards_title` 用法 → R3 顺序取代
- 置顶自我评价 / 主修课程罗列 → R5 删除
- 以匹配分高低决定选词或板块顺序 → R15 禁止
